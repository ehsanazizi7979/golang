Chapter 3 — Configuration and error handling

“Housekeeping”

Chapter 3 adds almost no functionality. Instead it reorganises the application so it can grow: configuration comes from flags, logging gets levels, dependencies are injected through an application struct, errors are centralised in helpers, and the routes move out of main(). It is the chapter that turns a working demo into something maintainable.

No figures in this chapter. Pages 62–85 are text and code only — the first chapter of the book without a single screenshot. Everything below is code the book prints, and each section links to the same behaviour running live in the demo.

3.1 · Managing configuration settings

main.go currently hard-codes two settings: the network address ":4000" and the static directory "./ui/static". That mixes configuration with code and makes it impossible to use different settings in development, testing and production. Go’s idiomatic fix is a command-line flag:

Terminalshell
$ go run ./cmd/web -addr=":80"
Defining the flaggo
addr := flag.String("addr", ":4000", "HTTP network address")

That line names the flag, sets its default and documents it. The value lands in addr at runtime — but only after flag.Parse() is called, and before the variable is used. The returned value is a pointer, hence the dereference when the address is used:

File: cmd/web/main.gogo
import (
    "flag" // New import
    "log"
    "net/http"
)

func main() {
    // Define a new command-line flag with the name 'addr', a default value of ":4000"
    // and some short help text explaining what the flag controls. The value of the
    // flag will be stored in the addr variable at runtime.
    addr := flag.String("addr", ":4000", "HTTP network address")

    // Importantly, we use the flag.Parse() function to parse the command-line flag.
    // This reads in the command-line flag value and assigns it to the addr
    // variable. You need to call this *before* you use the addr variable
    // otherwise it will always contain the default value of ":4000". If any errors are
    // encountered during parsing the application will be terminated.
    flag.Parse()

    mux := http.NewServeMux()
    fileServer := http.FileServer(http.Dir("./ui/static/"))
    mux.Handle("/static/", http.StripPrefix("/static", fileServer))

    mux.HandleFunc("/", home)
    mux.HandleFunc("/snippet/view", snippetView)
    mux.HandleFunc("/snippet/create", snippetCreate)

    // The value returned from the flag.String() function is a pointer to the flag
    // value, not the value itself. So we need to dereference the pointer (i.e.
    // prefix it with the * symbol) before using it. Note that we're using the
    // log.Printf() function to interpolate the address with the log message.
    log.Printf("Starting server on %s", *addr)
    err := http.ListenAndServe(*addr, mux)
    log.Fatal(err)
}

Three things worth knowing about flags: they are optional (omitting -addr falls back to ":4000"), they convert types automatically (flag.Int(), flag.Bool(), flag.Float64() fail fast on a bad value), and -help lists them all with the help text — free documentation:

Terminalshell
$ go run ./cmd/web -addr=":9999"
2022/01/29 15:50:20 Starting server on :9999

$ go run ./cmd/web -help
Usage of /tmp/go-build3672328037/b001/exe/web:
  -addr string
        HTTP network address (default ":4000")

Additional information. Environment variables look tempting, but os.Getenv() gives no default, no -help and always a string. The book’s compromise is to pass the environment variable as a flag: go run ./cmd/web -addr=$SNIPPETBOX_ADDR. Booleans accept a bare -flag (equal to -flag=true), and flag.StringVar() can parse directly into a field of a config struct. Ports 0–1023 need root, and give bind: permission denied.

Live: the demo server implements the same flag set. /config shows the values it actually parsed; node web/server.js -help prints the equivalent usage block.

3.2 · Leveled logging

So far logging uses the standard logger via log.Printf() and log.Fatal(), which stamps everything the same way and sends it all to stderr. The application has two kinds of message — informational and errors — and they deserve different treatment: INFO to stdout, ERROR to stderr with the calling file and line. Two custom loggers do it:

File: cmd/web/main.go — the two loggersgo
// Use log.New() to create a logger for writing information messages. This takes
// three parameters: the destination to write the logs to (os.Stdout), a string
// prefix for message (INFO followed by a tab), and flags to indicate what
// additional information to include (local date and time). Note that the flags
// are joined using the bitwise OR operator |.
infoLog := log.New(os.Stdout, "INFO\t", log.Ldate|log.Ltime)

// Create a logger for writing error messages in the same way, but use stderr as
// the destination and use the log.Lshortfile flag to include the relevant
// file name and line number.
errorLog := log.New(os.Stderr, "ERROR\t", log.Ldate|log.Ltime|log.Lshortfile)

infoLog.Printf("Starting server on %s", *addr)
err := http.ListenAndServe(*addr, mux)
errorLog.Fatal(err)

Running a second copy of the server produces the two prefixes side by side, and note the main.go:37 on the error line:

Terminal — the address is already in useshell
$ go run ./cmd/web
INFO    2022/01/29 16:00:50 Starting server on :4000
ERROR   2022/01/29 16:00:50 main.go:37: listen tcp :4000: bind: address already in use
exit status 1

Because the loggers write to the standard streams, logging stays decoupled from the application: the execution environment decides where the output ends up, simply by redirecting it.

Terminal — redirecting the streamsshell
$ go run ./cmd/web >>/tmp/info.log 2>>/tmp/error.log

One loose end: Go’s HTTP server logs its own problems with the standard logger. Wrapping the server in an http.Server struct lets it share errorLog:

File: cmd/web/main.go — replacing ListenAndServe()go
// Initialize a new http.Server struct. We set the Addr and Handler fields so
// that the server uses the same network address and routes as before, and set
// the ErrorLog field so that the server now uses the custom errorLog logger in
// the event of any problems.
srv := &http.Server{
    Addr:     *addr,
    ErrorLog: errorLog,
    Handler:  mux,
}

infoLog.Printf("Starting server on %s", *addr)
err := srv.ListenAndServe()
errorLog.Fatal(err)

Additional information. Avoid Panic() and Fatal() outside main() — return errors instead. Loggers from log.New() are concurrency-safe, so one logger can be shared across goroutines and handlers; if several loggers share a destination, that Write() must be safe too. log.Llongfile gives the full path and log.LUTC forces UTC timestamps.

Live: /logs streams this server’s real stdout/stderr output — INFO lines without a file reference, ERROR lines with one, exactly like the book.

3.3 · Dependency injection

The home handler still calls log.Print(), i.e. the standard logger, instead of the new errorLog. How does a handler in handlers.go reach a value created in main()? The same question applies to every future dependency: a database pool, a template cache, a session manager.

Globals are the simplest answer and the wrong one — they are implicit, error-prone and hard to test. Instead, put the dependencies in a struct and make the handlers methods on it:

File: cmd/web/main.go — the application structgo
// Define an application struct to hold the application-wide dependencies for the
// web application. For now we'll only include fields for the two custom loggers, but
// we'll add more to it as the build progresses.
type application struct {
    errorLog *log.Logger
    infoLog  *log.Logger
}

func main() {
    ...
    // Initialize a new instance of our application struct, containing the
    // dependencies.
    app := &application{
        errorLog: errorLog,
        infoLog:  infoLog,
    }

    mux := http.NewServeMux()
    fileServer := http.FileServer(http.Dir("./ui/static/"))
    mux.Handle("/static/", http.StripPrefix("/static", fileServer))

    mux.HandleFunc("/", app.home)
    mux.HandleFunc("/snippet/view", app.snippetView)
    mux.HandleFunc("/snippet/create", app.snippetCreate)
    ...
}
File: cmd/web/handlers.go — methods, not functionsgo
// Change the signature of the home handler so it is defined as a method against
// *application.
func (app *application) home(w http.ResponseWriter, r *http.Request) {
    ...
    ts, err := template.ParseFiles(files...)
    if err != nil {
        // Because the home handler function is now a method against application
        // it can access its fields, including the error logger. We'll write the log
        // message to this instead of the standard logger.
        app.errorLog.Print(err.Error())
        http.Error(w, "Internal Server Error", 500)
        return
    }
    ...
}

It looks like ceremony for two loggers — and the book admits as much — but the pattern pays off as the struct grows. To prove it works, the book deliberately breaks the app: rename home.tmpl and request the home page.

Terminalshell
$ mv ui/html/pages/home.tmpl ui/html/pages/home.bak
$ go run ./cmd/web
INFO    2022/01/29 16:12:36 Starting server on :4000
ERROR   2022/01/29 16:12:40 handlers.go:29: open ./ui/html/pages/home.tmpl: no such file or directory

The ERROR prefix and the handlers.go reference prove the logger travelled from main() into the handler as a dependency. (The book leaves the error in place — the next section needs it.)

Additional information. This pattern does not work when handlers live in several packages. The alternative is a config package with an exported Application struct, and handlers as closures: examplePackage.ExampleHandler(app) returns an http.HandlerFunc that closes over the struct.

Live: /break toggles exactly this failure. Switch it on, request /home, and the log shows the ERROR line with the handler’s file and line.

3.4 · Centralized error handling

Error handling now repeats itself in every handler. Three small helpers on the application struct fix that — serverError logs the error plus a stack trace and sends a generic 500, clientError sends any 4xx/5xx with its standard description, and notFound wraps the 404 case.

File: cmd/web/helpers.gogo
package main

import (
    "fmt"
    "net/http"
    "runtime/debug"
)

// The serverError helper writes an error message and stack trace to the errorLog,
// then sends a generic 500 Internal Server Error response to the user.
func (app *application) serverError(w http.ResponseWriter, err error) {
    trace := fmt.Sprintf("%s\n%s", err.Error(), debug.Stack())
    app.errorLog.Print(trace)
    http.Error(w, http.StatusText(http.StatusInternalServerError), http.StatusInternalServerError)
}

// The clientError helper sends a specific status code and corresponding description
// to the user. We'll use this later in the book to send responses like 400 "Bad
// Request" when there's a problem with the request that the user sent.
func (app *application) clientError(w http.ResponseWriter, status int) {
    http.Error(w, http.StatusText(status), status)
}

// For consistency, we'll also implement a notFound helper. This is simply a
// convenience wrapper around clientError which sends a 404 Not Found response to
// the user.
func (app *application) notFound(w http.ResponseWriter) {
    app.clientError(w, http.StatusNotFound)
}

debug.Stack() captures the current goroutine’s execution path, which is what makes an error message debuggable; http.StatusText() turns 400 into "Bad Request" for you. The handlers then shrink to calls like app.serverError(w, err), app.notFound(w) and app.clientError(w, http.StatusMethodNotAllowed).

The first attempt has a flaw. The log line now reports helpers.go:13 — the place the message is written — rather than the handler that hit the error:

$ go run ./cmd/web
INFO    2022/01/29 16:22:14 Starting server on :4000
ERROR   2022/01/29 16:22:19 helpers.go:13: open ./ui/html/pages/home.tmpl: no such file or directory
goroutine 6 [running]:
runtime/debug.Stack()
        /usr/local/go/src/runtime/debug/stack.go:24 +0x65
main.(*application).serverError(...)
        /home/alex/Desktop/snippetbox.v2/cmd/web/helpers.go:12 +0x66

        /home/alex/Desktop/snippetbox.v2/cmd/web/handlers.go:24 +0x194

The fix is Output() with a calldepth of 2, which tells the logger to report the caller one frame further up:

File: cmd/web/helpers.go — correctedgo
func (app *application) serverError(w http.ResponseWriter, err error) {
    trace := fmt.Sprintf("%s\n%s", err.Error(), debug.Stack())
    app.errorLog.Output(2, trace)
    http.Error(w, http.StatusText(http.StatusInternalServerError), http.StatusInternalServerError)
}
Terminal — correct originshell
$ go run ./cmd/web
INFO    2022/01/29 16:24:00 Starting server on :4000
ERROR   2022/01/29 16:24:02 handlers.go:24: open ./ui/html/pages/home.tmpl: no such file or directory

The deliberate error is no longer needed: mv ui/html/pages/home.bak ui/html/pages/home.tmpl.

3.5 · Isolating the application routes

main() is getting crowded. The route declarations move into their own file, as a method on the application struct:

File: cmd/web/routes.gogo
package main

import "net/http"

// The routes() method returns a servemux containing our application routes.
func (app *application) routes() *http.ServeMux {
    mux := http.NewServeMux()

    fileServer := http.FileServer(http.Dir("./ui/static/"))
    mux.Handle("/static/", http.StripPrefix("/static", fileServer))

    mux.HandleFunc("/", app.home)
    mux.HandleFunc("/snippet/view", app.snippetView)
    mux.HandleFunc("/snippet/create", app.snippetCreate)

    return mux
}
File: cmd/web/main.go — the whole function, at lastgo
func main() {
    addr := flag.String("addr", ":4000", "HTTP network address")

    flag.Parse()

    infoLog := log.New(os.Stdout, "INFO\t", log.Ldate|log.Ltime)
    errorLog := log.New(os.Stderr, "ERROR\t", log.Ldate|log.Ltime|log.Lshortfile)

    app := &application{
        errorLog: errorLog,
        infoLog:  infoLog,
    }

    srv := &http.Server{
        Addr:     *addr,
        ErrorLog: errorLog,
        // Call the new app.routes() method to get the servemux containing our routes.
        Handler: app.routes(),
    }

    infoLog.Printf("Starting server on %s", *addr)
    err := srv.ListenAndServe()
    errorLog.Fatal(err)
}

And with that, main() does exactly three things: parse configuration, establish dependencies, run the server. Everything else now has a home.
